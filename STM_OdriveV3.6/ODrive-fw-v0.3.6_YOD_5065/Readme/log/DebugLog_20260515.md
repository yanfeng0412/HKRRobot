## 问题一：重新校准时报 ERROR_PHASE_RESISTANCE_TIMING

**现象：** 第一次上电校准成功，发 `$M0,H,0;` 后再发 `$M0,V,5.0;` 触发重标定时，概率性出现 timing 错误。  
**根本原因：** `motor_thread` 进入 `motor_calibration()` 之前，`M_SIGNAL_PH_CURRENT_MEAS` 信号位已被 ADC IRQ 置位（PWM 关闭期间 TIM1 依然触发 ADC，ADC IRQ 持续调用 `osSignalSet`）。`measure_phase_resistance()` 中第一次 `osSignalWait()` 立刻返回积压信号，此时 TIM8 CNT 处于随机相位；若处于下计数区间，`check_timing` 读到 `timing ≈ 2×PERIOD > 1.5×PERIOD`（deadline）→ `ERROR_PHASE_RESISTANCE_TIMING`。  
**解决方案：** 在调用 `motor_calibration()` 前用 `osSignalWait(signal, 0)`（非阻塞，timeout=0）消耗积压信号：

```c
// low_level.c — motor_thread
if (motor->do_calibration == false) {
    __HAL_TIM_MOE_ENABLE(motor->motor_timer);
    osSignalWait(M_SIGNAL_PH_CURRENT_MEAS, 0);  // 消耗积压信号，避免随机 CNT
    motor_calibration(motor);
    __HAL_TIM_MOE_DISABLE_UNCONDITIONALLY(motor->motor_timer);
    motor->do_calibration = true;
}
```

> **注：** CMSIS-RTOS v1 包装层没有实现 `osSignalClear`，用 `osSignalWait(signal, 0)` 代替（非阻塞消耗信号位）。

## 问题二：进入控制环时电流尖峰（积分器残值）

**现象：** H 停止后再次发 V 启动时，Iq 在第一帧就达到 3-5A，导致电机抖动一下。  
**根本原因：** `motor_thread` 重新进入 `control_motor_loop()` 时，`vel_integrator_current` 保留上一次运行的残值（可能为正或负数安培），叠加到当前速度误差产生的 P 项上，导致启动瞬间过大电流。同时 ADC 信号积压（同问题一机理）也会造成首帧 FOC_TIMING 错误。  
**解决方案：** 进入控制环前清空积分器并 drain 信号：

```c
// low_level.c — motor_thread
osSignalWait(M_SIGNAL_PH_CURRENT_MEAS, 0);   // drain stale ADC signals
motor->vel_integrator_current = 0.0f;         // 重置积分器，防电流冲击
bool spin_up_ok = true;
if (motor->rotor_mode == ROTOR_MODE_SENSORLESS) spin_up_ok = spin_up_sensorless(motor);
if (spin_up_ok) control_motor_loop(motor);
```

## 问题三：新增 ERROR_MOTOR_STALL (code 24) + 堵转守卫

**背景：** Hall 模式下电机堵转时，速度控制器会持续输出最大限流（20A），长时间堵转损伤 DRV8301 和绕组。  
**解决方案：** 在 `control_motor_loop` 中添加 3 秒 Hall 模式堵转检测：

```c
// low_level.h — Error_t 新增
ERROR_MOTOR_STALL, //24  Hall 电机堵转超 3 s

// low_level.c — control_motor_loop
// Hall-mode stall watchdog
if (motor->rotor_mode == ROTOR_MODE_HALL &&
    motor->control_mode >= CTRL_MODE_VELOCITY_CONTROL &&
    fabsf(vel_des) > 2.0f) {
    static uint32_t hall_stall_cnt[2] = {0, 0};
    int midx = (motor == &motors[0]) ? 0 : 1;
    if (fabsf(get_pll_vel(motor)) < 2.0f) {
        if (++hall_stall_cnt[midx] > (uint32_t)(3.0f * current_meas_hz)) {
            motor->error = ERROR_MOTOR_STALL;
            break;
        }
    } else {
        hall_stall_cnt[midx] = 0;
    }
}
```

## 问题四：M1 Hall-C 引脚冲突（PB3 与 SWO 复用）

**现象：** M1 Hall-C 接 PB3（原 ENC_Z），JTAG SWO 调试输出干扰 Hall 读数，偶发 Hall 状态 =7（无效）。  
**根本原因：** PB3 同时是 `SYS_JTDO-SWO`，JTAG 调试期间 SWO 输出会污染 GPIO 读值。  
**解决方案：** 将 M1 Hall-C 改接 PC15（M1_DC_CAL 焊盘复用为数字输入）：

```c
// Inc/main.h
#define M1_ENC_Z_Pin        GPIO_PIN_15
#define M1_ENC_Z_GPIO_Port  GPIOC
```

```c
// Inc/app_config.h
#define APP_M1_HALL_C_PORT   GPIOC
#define APP_M1_HALL_C_PIN    GPIO_PIN_15   /* PC15 = M1_DC_CAL 复用 */
```

> **注：** PC15 与 M0_ENC_Z（PC9 区间 EXTI15_10）共享中断线，但 Hall 检测用轮询模式，不依赖 EXTI，无影响。

## 问题五：M1 Hall 初始化参数缺失

**现象：** M1 motors[1] 初始化器中 Hall GPIO 结构引用了 M0 的 PORT/PIN 宏，M1 Hall 状态读取结果实为 M0 的输入值。  
**根本原因：** 添加 M1 通道时，`low_level.c` 的 `motors[1]` 初始化器中 Hall 相关字段沿用了 M0 的宏定义（未区分 M0/M1）。  
**解决方案：** 在 `app_config.h` 中添加 M1 专用宏，并在 `motors[1]` 初始化器中引用：

```c
// Inc/app_config.h — M1 专用 Hall 宏
#define APP_M1_HALL_A_PORT       GPIOB
#define APP_M1_HALL_A_PIN        GPIO_PIN_6    /* M1_ENC_A / PB6 */
#define APP_M1_HALL_B_PORT       GPIOB
#define APP_M1_HALL_B_PIN        GPIO_PIN_7    /* M1_ENC_B / PB7 */
#define APP_M1_HALL_C_PORT       GPIOC
#define APP_M1_HALL_C_PIN        GPIO_PIN_15   /* M1_DC_CAL 复用 / PC15 */
#define APP_M1_HALL_MOTOR_DIR      1
#define APP_M1_HALL_PHASE_OFFSET   3.5f
```

## 问题七：同时发送双命令 `$M0,V,5.0;$M1,V,5.0;` M1 不响应

**现象：** 在同一帧发送两条命令，板子只执行 M0，M1 命令丢失或延迟几秒才执行。  
**根本原因：** UART 解析器只识别 `\r/\n/!` 作为帧结束符，`;` 被当普通字符存入 `parse_buffer`。sscanf 解析整行 buffer 时只能识别第一条 `M0,...`，第二条 `$M1,...` 因为已过 `sscanf` 起点而被丢弃。  
**解决方案：** 将 `;` 也作为帧结束符，处理完当前命令后**不退出** while 循环（不设 `reset_read_state=true`），继续消耗 DMA 缓冲区中后续字节：

```c
// commands.c — cmd_parse_thread 内层 while
if (c == ';') {
    parse_buffer[parse_buffer_idx - 1] = '\0';
    if (parse_buffer_idx > 1)
        motor_parse_cmd(parse_buffer, parse_buffer_idx, SERIAL_PRINTF_IS_UART);
    // 重置 parse 状态但不 break → 继续消耗 DMA buffer
    parse_buffer_idx = 0;
    read_active = false;
} else if (c == '\r' || c == '\n' || c == '!') {
    // 旧格式兼容
    parse_buffer[parse_buffer_idx-1] = '\0';
    if (parse_buffer_idx > 1)
        motor_parse_cmd(parse_buffer, parse_buffer_idx, SERIAL_PRINTF_IS_UART);
    reset_read_state = true;
    break;
}
```

**效果：**

| 发送格式 | 结果 |
|---------|------|
| `$M0,V,5.0;$M1,V,5.0;` | M0、M1 均执行 ✓ |
| `$M0,H,0;$M1,H,0;$M0,V,3.0;` | 三条命令全部执行 ✓ |
| `$M0,V,5.0\n`（旧格式） | 仍然有效 ✓ |

## 问题八：M0 电机方向反转（错误方式导致噪声）

**现象 A：** M0 实际旋转方向与期望相反（`$M0,V,5.0;` 应正转但实际反转）。  
**错误处理：** 将 `APP_HALL_MOTOR_DIR` 从 1 改为 -1。结果：M0 出现剧烈抖动+噪声，M1（仍为 dir=1）正常安静。  

**根本原因分析（motor_dir 不能用于反转方向）：**

`motor_dir` 是 **FOC 校准参数**，同时影响两处核心计算：

```
hall_phase_from_pos():
    phase = (2π/6) × (pll_pos − phase_offset) × motor_dir   ← 定子磁场角度

get_pll_vel():
    vel = pll_vel × (2π/6) / pole_pairs × motor_dir          ← 速度反馈符号
```

`phase_offset = 3.5f` 是在 `motor_dir = 1` 下校准的。改成 `-1` 后，相位公式中增加一个负号但 offset 未重新校准，FOC 磁场角度偏离实际转子约 120°~180°，产生抖动和噪声。

**正确修复：** 在指令层对速度值施加符号翻转，FOC 校准参数不动：

```c
// Inc/app_config.h — 新增应用层方向宏
#define APP_HALL_MOTOR_DIR     1        /* FOC 校准值，勿修改 */
#define APP_HALL_PHASE_OFFSET  3.5f

#define APP_M0_VEL_DIRECTION  (-1)      /* M0 输出反向（正命令→反转） */
#define APP_M1_VEL_DIRECTION    1       /* M1 正向 */

// commands.c — V 命令处理，转换后乘以方向系数
static const int8_t app_dir[2] = { APP_M0_VEL_DIRECTION, APP_M1_VEL_DIRECTION };
vel_rad_s *= (float)app_dir[motor_idx];
```

> **经验：** 如需翻转任意通道输出方向，只改 `APP_Mx_VEL_DIRECTION`（1 或 -1），不要动 `APP_HALL_MOTOR_DIR`。

## 问题九：M0 抖动/噪声（积分增益和 PLL 带宽偏高）

**现象：** M0 运行时有轻微抖动和可闻噪声，M1 正常，而两者配置宏相同。（注：此问题在 motor_dir 错误问题修复后通过降增益进一步优化）  
**根本原因：** Hall CPR=6，每机械圈仅 6 次速度更新（约 18 ms/次 at 5 km/h）。速度估计存在固有量化噪声。`vel_integrator_gain = 0.04` 在高 P 增益（`vel_gain = 0.02`）下放大了 Hall sector 边沿触发的 `pll_vel` 修正脉冲，通过 PI 转化为 Iq 纹波，导致电机线圈振动可闻。  

**每次 Hall 边沿的 pll_vel 冲击量：**

```
冲击 = dt × pll_ki × delta_pos
pll_ki = 0.25 × BW² = 0.25 × 200² = 10000   (BW=200 rad/s 时)
冲击 ≈ 120µs × 10000 × 1 ≈ 1.2 counts/s/sample
```

**解决方案：** 降低积分增益，PLL 带宽保持不变（稳态精度不受影响，PLL 是二阶系统）：

```c
// Inc/app_config.h
#define APP_VEL_GAIN                 0.02f  /* [A/(rad/s)] */
#define APP_VEL_INTEGRATOR_GAIN      0.01f  /* 从 0.04 降至 0.01，减少 Hall 量化噪声放大 */
```

| 参数 | 旧值 | 新值 | 变化 |
|------|------|------|------|
| vel_gain | 0.01 | 0.02 | ×2（保证即时启动 P 项） |
| vel_integrator_gain | 0.04 | 0.01 | ÷4（减少积分器追噪声） |

## 问题十：M1 启动力矩明显弱于 M0（有载条件下）

### 现象

同一车架（相近负载），相同参数配置，相同命令 `$M1,V,5.0;` 与 `$M0,V,5.0;`：

- 空载：两通道行为一致，差异不明显
- **有载（车架自重）：M1 明显起步迟滞或需要更高速度命令才能启动**
- 重新校准后无改善
- 机械不对称性不足以解释该差异

### 排查过程

| 步骤 | 结论 |
|------|------|
| 扫描 `APP_M1_HALL_PHASE_OFFSET`：2.5 / 3.0 / **3.5** / 4.0 / 4.5 | 3.5f 仍是最优，其他值导致抖动/堵转/反转 |
| 重新校准 | 无改善 |
| 机械负载对称性 | 装配差异存在，但不至于引起如此明显力矩差异 |

**结论：phase_offset 不是根因（已排除）。**

### 根本原因分析

#### 原因 A（高可信度）：ADC Regular 被 Injected 抢占 → M1 电流采样点漂移

M0 / M1 在 ADC 架构上存在**非对称设计**：

| | M0 | M1 |
|---|---|---|
| 采样触发 | TIM1_TRGO → **Injected** ADC（最高优先级） | TIM8_TRGO → **Regular** ADC（可被打断） |
| 采样保护 | 不会被抢占 | 会被 Injected 事件打断 |

**STM32 规则：Injected 转换会强制抢占（打断）正在进行的 Regular 转换。**

TIM1 和 TIM8 同频（~8.2 kHz）、未锁相（`TIM_MASTERSLAVEMODE_DISABLE`），两路触发相位会周期性漂移。当相位接近重叠时：

```
TIM8 触发 M1 Regular ADC 开始采样
  → 几十纳秒后 TIM1 触发 M0 Injected → 抢占 M1 采样
  → M0 采完后 M1 重新采样
  → M1 采样点偏离 PWM 中心（本应是零矢量中点）
  → ADC 读取到的是相电流的纹波部分，而非真实平均值
  → DC_calib 只校正直流偏置，无法补偿这种相位漂移误差
  → M1 电流反馈带有系统性误差 → PI 调节器基于错误反馈工作
  → 有效力矩减少
```

空载时误差影响小（力矩需求低），**有载起步时误差被放大**。

#### 原因 B（中可信度）：M1 电流环增益与 M0 不同

校准后的 `p_gain = BW × L`，`i_gain = (R/L) × p_gain`。

若 M1 校准测量到的 `phase_inductance` 略低于 M0（制造批次差异、或 ADC 噪声影响校准精度），则 M1 电流环带宽更低，电流爬升更慢，起步时力矩上升速率弱于 M0。

**验证方法：** 通过 UART Q 命令读取两通道校准值：
```
// 对比 M0_PHASE_INDUCTANCE vs M1_PHASE_INDUCTANCE
// 对比 M0_PHASE_RESISTANCE vs M1_PHASE_RESISTANCE
```
若 L 相差 > 15%，可为 M1 单独提高电流环带宽宏补偿。

#### 原因 C（低可信度）：control_deadline 不对称

- M0：`control_deadline = TIM_1_8_PERIOD_CLOCKS`（1×周期）
- M1：`control_deadline = (3 × TIM_1_8_PERIOD_CLOCKS) / 2`（1.5×周期）

M1 控制截止时间更宽松，意味着 M1 的 FOC 计算结果更新频率更低（允许更长延迟），在动态响应上天然比 M0 慢半拍。

### 临时解决方案（已实施）

将 M0 / M1 的起步前馈电流分离为独立宏：

```c
// Inc/app_config.h
#define APP_M0_HALL_STARTUP_CURRENT  2.0f    // [A] M0 保持不变
#define APP_M1_HALL_STARTUP_CURRENT  4.0f    // [A] M1 提高，补偿采样误差带来的力矩损失
```

`low_level.c` 中的启动前馈逻辑按 motor index 查表选取对应阈值。

**效果：** M1 有载起步力矩恢复正常，但这是 workaround，不是根治。

### 待做（后期）

| 优先级 | 方案 | 说明 |
|--------|------|------|
| ★★★ | 读取 Q 命令，对比 M0/M1 的 R/L 校准值 | 确认原因 B 是否成立 |
| ★★★ | 将 TIM8 配置为 TIM1 的 Slave，锁相 180° | 从硬件上消除 ADC 采样竞争（根治原因 A），需改 `tim.c` 初始化顺序，有一定风险 |
| ★★ | 若 R/L 差异 > 15%，为 M1 添加独立电流环带宽宏 | 补偿原因 B |
| ★ | 评估是否需要修正 M1 的 `control_deadline` | 对齐 M0/M1 控制延迟 |

> **关键提醒：** TIM8 锁相改动涉及 `MX_TIM8_Init()` 及启动时序，改动前务必备份当前 `tim.c`，并在空载条件下验证两路 ADC 回调不发生竞争后再上载测试。
